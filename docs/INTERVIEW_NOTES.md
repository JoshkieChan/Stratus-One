# Interview notes

- **Problem:** Small proposal teams need to track opportunities, tasks, estimates and decisions together rather than across disconnected lists.
- **User flow:** Choose an opportunity → review scope/deadline/value → organize task packs → complete proposal work → price a quote → update pipeline status.
- **Architecture:** Shared React screens call typed service facades. Demo adapters use tab-local fixtures; hosted adapters use Supabase. This makes the real interface reviewable without cloud provisioning. Pure domain functions hold reusable calculations and scoring; UI components retain the original design language.
- **Quote logic:** Validate finite, nonnegative quantities/prices and a fractional tax rate between zero and one. Round each line to cents, sum subtotal, round tax, then total. PostgreSQL independently recalculates persisted amounts with numeric arithmetic. Version predicates prevent stale updates from overwriting newer edits; the editor keeps unsaved input after a conflict.
- **RLS and ownership:** Every business table restricts operations to its owner. Composite foreign keys ensure quotes/tasks/packs reference an opportunity owned by the same user and that task packs match their opportunity. Profile metadata is user-editable display information, never an authorization source. Edge Functions validate the caller and retain caller-scoped database access.
- **Difficult issue:** The original entry point only mounted a design gallery. Making the real workspace independently runnable required isolating eager Supabase initialization, sharing service contracts, and preserving authentication in hosted mode. Browser checks then caught a narrow dropdown caused by a design-token/Tailwind sizing collision that interaction tests alone missed.
- **Evidence to discuss:** Unit tests for quotes/scoring, service error tests, actual Postgres RLS/constraint tests, and Chromium walkthroughs covering local saves/reloads, reset, mobile navigation and quote conflicts.
- **Honest limitation:** Hosted Auth/Data API/functions still need end-to-end verification in a dedicated Supabase project. The demo proves UI/workflow behavior, not hosted deployment. Browser-based quote arithmetic is appropriate for estimates, not an accounting system.
- **Attribution and ownership:** Explain the Figma-export visual origin openly. Be prepared to explain the refactoring, adapters, schema, tests and tradeoffs in your own words; only claim implementation work you can substantiate and discuss.
